## 第一部分 · 脱离仓库：从问题本身推导

> 本部分**不引用任何仓库文件**。假设我们昨天才拿到"做一个概率论 AI 伴学工具"这个题目，
> 从头想清楚"谁需要它、需要它做什么、什么算做成了"。

### 1. 先把"用户"拆开——不是一个用户，是四个

很多学生项目失败在把"学生"当成一个人。实际上至少有四种人能影响这个产品的成败，**他们的成功标准互相冲突**：

| 角色 | 真实处境 | 他要的 | 他不关心 |
|---|---|---|---|
| **S1 正在写作业的学生** | 有 deadline，要的是**这道题怎么算**，现在就要 | 快、准、步骤能抄 | 不许要注册、不许要我读完说明书 |
| **S2 备考的学生** | 要的是**我哪里不会**，以及反复练 | 薄弱点定位、能重做、有进度 | 单题的漂亮讲解 |
| **S3 任课教师** | 关心**学生是否真在学**、会不会被代做 | 能否被我看见、能否证明有效 | 架构多先进 |
| **S4 项目组/评委** | 关心**这事有没有技术含量、能不能讲清楚** | 可验证、可复现的数字 | 界面好不好看 |

**关键推论**：S1 和 S2 要的东西**方向相反**——S1 要"最快拿到答案"，S2 要"让我自己想出来"。一个界面同时服务两者必然撕裂。这解释了为什么"悬浮窗"和"主站"两个形态**不是产品包装问题，而是需求分层问题**：悬浮窗服务 S1（就着眼前的页面问），主站服务 S2（沉淀、练习、追踪）。**仓库后来独立走到了同一个结论**（见第二部分 §3.4）。

> ⚠️ 但这里埋着一个危险：**如果工具太擅长服务 S1，它就变成"作业代写器"**，直接威胁 S3（教师）的接受度。这是一个**需求层面的伦理约束**，不是功能层面的（详见 §5）。

### 2. 概率论这门课特殊在哪？

换一门课（比如英语单词），需求会完全不同。概率论有四个性质，直接决定产品形态：

| 性质 | 后果 |
|---|---|
| **答案几乎总是一个可验证的数值或表达式** | ★ **这是最大的机会**：正确性可以被机器证明。英语作文不行，历史论述不行，概率论行 |
| **但"过程"比"答案"重要** | 学生错的往往不是算错，而是**建模错**（把 P(A\|B) 和 P(B\|A) 搞反、漏掉完备事件组）。只给答案没用 |
| **错误高度模式化** | 贝叶斯方向颠倒、独立与互斥混淆、忽略 n 次试验的独立性……**错误种类是有限且可枚举的** |
| **依赖关系强** | 不会条件概率就学不会贝叶斯；不会期望就学不会方差。**知识点是有向图，不是列表** |

**推论 1**：因为答案可验证，"**告诉学生这个答案经过了几层验证**"能成为真卖点——这在文科类工具里根本做不到。

**推论 2**：因为错误模式化且有限（可能就 50–100 条），"**告诉学生你踩了哪个坑**"比"再讲一遍知识点"有效得多，而且**不需要任何学生数据**就能做（从教材、教师经验整理即可）。

**推论 3**：因为依赖关系强，错题本不能只记"这道题错了"，必须记"**这道题考了哪几个知识点**"，才能沿依赖图往上找根源。**这一条决定了数据模型**（见 §4.2）。

### 3. 从"学生的一次挫败"倒推功能

不要列功能清单。跟着一次真实的挫败走一遍，功能会自己长出来。

```
场景：学生做到一道贝叶斯题，卡住了。

① 他不知道这题在问什么            → 需求：题目能看懂 / 能拆解
② 他隐约记得有个公式但想不起来     → 需求：精准的公式/定理查找（不是泛泛讲解）
③ 他试着写了一个式子，不确定对不对 → 需求：逐步判定，指出第一处错在哪
④ 他算完了，但答案是 0.99         → 需求：即时批改 + 诊断"你把方向搞反了"
⑤ 他改对了，但不知道为什么对       → 需求：解析 + 这一步的依据（教材出处）
⑥ 一周后他又错了同一类题           → 需求：错题本按知识点归类 + 能重做
⑦ 他连着错了三道贝叶斯题           → 需求：沿知识依赖往上找，是不是条件概率就没懂
                                           → 需求：给出复习路径，而不是"再练 10 道"
```

**七个环节，缺一环闭环就断**。特别要注意 ⑥⑦ 与 ①–⑤ 是**两种不同类型的需求**：

- ①–⑤ 是**单次会话内**的需求 → 无状态、可随时丢弃
- ⑥–⑦ 是**跨会话**的需求 → **必须有持久化的作答记录**

**这是全篇最重要的推论**：任何声称"伴学"的工具，如果没有⑧（持久化作答记录），它其实只是个"答疑工具"。**"学习"这个词承诺的是时间维度上的变化，而没有记录就没有变化可谈。**

### 4. 需求清单（F = 功能，N = 非功能）

按"缺了它产品是否成立"分三级：**MUST / SHOULD / MAY**。

#### 4.1 功能性需求

| ID | 需求 | 级别 | 验收方式（可断言） |
|---|---|---|---|
| **F1** | 学生能就**当前正在看的内容**提问（读屏） | MUST | 注入后能正确报出：所在章节、正文摘要、选中文字 |
| **F2** | 系统能解题并给出**可读的逐步过程** | MUST | 给定题目，输出步骤数 ≥3 且每步可复述 |
| **F3** | 解答带**正确性声明**（这次验证到什么程度） | MUST | 每条解答都携带级别标签，无标签不出结果 |
| **F4** | 学生提交作答后**即时判定**（不依赖大模型往返） | MUST | 纯计算题端到端 < 1s |
| **F5** | 判定错误时给出**针对性的错因**，而非"答错了" | MUST | 命中预定错误模式时输出对应解释 |
| **F6** | 提供**分级提示**（先给方向，再给步骤，最后才给解析） | MUST | 提示阶梯可用；未提交前不出现完整解析 |
| **F7** | 每次作答**留下结构化记录** | MUST | 每条记录含：题目、作答、对错、知识点、用时、用了几次提示 |
| **F8** | 错题可按**知识点**归类，并支持重做 | SHOULD | 能列出"贝叶斯类错了 3 道"并可重做 |
| **F9** | 知识点之间的**依赖关系**可见，并能沿依赖回溯 | SHOULD | 存在知识点图；错误可上溯到前置知识点 |
| **F10** | 解答能**引用教材出处**（章节/行），可核对 | SHOULD | 检索命中带出处；无命中时如实说明 |
| **F11** | 学生能看到**自己学到哪了**（进度/薄弱） | SHOULD | 有进度视图，数据来源于 F7 的记录 |
| **F12** | 可视化辅助（分布曲线、交互动画） | MAY | 8 个动画可播放、分布图可交互 |
| **F13** | 多智能体协作过程对用户/评委**可见** | MAY | 协作轨迹可回放 |

> **注意 F4 的措辞**："不依赖大模型往返"。理由：批改是**确定性**问题（答案是数值，比较即可），用概率模型去解确定性问题，既慢又引入了本可避免的误差。**这个判断独立于任何实现**——哪怕将来模型再快，确定性问题不该交给它。

#### 4.2 非功能性需求

| ID | 需求 | 级别 | 为什么它对本项目特别重要 |
|---|---|---|---|
| **N1** | **正确性可验证**：错误答案必须被拦住或标注 | MUST | 唯一的技术差异化。学生无法判断答案对错，**误信的代价由学生承担** |
| **N2** | **诚实**：做不到的事必须明说，不许笼统说"已校验" | MUST | 学习工具的信任是一次性的，骗一次就永久失去 |
| **N3** | **数据不出校**（可本地/局域网运行） | MUST | 教材版权 + 学生数据合规；也是"能否给老师看"的前提 |
| **N4** | **无需安装即用**（学生不会为一次作业装环境） | MUST | 决定实际使用率；S1 的耐心 ≈ 0 |
| **N5** | **不篡改课平台**（只读，不代点、不注入视觉元素） | MUST | 一旦修改宿主页面，从"辅助工具"变成"篡改平台内容"，合规风险陡增 |
| **N6** | **可归属会话，且无 PII**（不收集学号/姓名） | MUST | 既满足 ⑥⑦ 的持久化，又不触发个人信息保护的合规门槛。**2026-09 修正**：为支持多账号与两种角色，改用具名账号；账号为**化名**（不采集学号/真实姓名），密码只存 bcrypt 哈希，数据仍只落本地库，并提供"删除我的数据"入口 |
| **N7** | **响应及时**：单题反馈 < 1s，讲解首字 < 2s | SHOULD | 超时就回到"问搜索引擎"的行为了 |
| **N8** | **可访问、可读**：对比度达标、键盘可用 | SHOULD | 学习工具的可及性；也是评奖时的加分项 |
| **N9** | **可复现的效果数据**：能说"这一版比上一版好多少" | SHOULD | 对 S4；没有它所有改进都无法证明 |
| **N10** | **多端可用**（至少手机能看错题本） | MAY | 复习发生在碎片时间 |

### 5. ★ 一条需求层面的伦理约束（不是功能）

**F1–F6 做得越好，工具越接近"作业代写器"。** 这是需求内在的矛盾，必须在产品层面缓解：

| 缓解手段 | 机制 |
|---|---|
| **提示阶梯（F6）** | 默认先给方向，完整解析需要学生先尝试——把"抄答案"变成"要点两下"的摩擦 |
| **不做"直接出最终答案"的入口** | 把"结论"放在"过程"之后 |
| **教师可见（可选的 F8 聚合视图）** | 让 S3 知道工具在干什么，而不是被绕过 |
| **对"用了 3 次提示才答对"如实记入掌握度** | 数据上不美化（这正是 `hint_used` 字段存在的理由） |

> 推论：**"提示阶梯"不是体验优化，是伦理约束落地的地方**。它必须在数据模型里有对应字段（用了几次提示），否则约束无法执行、也无法度量。

### 6. 什么算"做成了"——成功标准

脱离实现，先定验收线：

| 维度 | 达标线 | 怎么测 |
|---|---|---|
| 解题正确率 | 在自建题库上 ≥ 基线水平（**必须有基线**） | 固定题集 + 固定评分脚本 |
| **错误拦截率** | 注入的错误解答**必须被发现**或降级标注 | 注入已知错解，统计拦截率 |
| **诚实性** | 标注级别与实际验证手段**一致率达 100%** | 抽查：标 A 的是否真做了重算 |
| 批改准确率 | 数值题 100%（确定性代码）；应用题可接受误差 | 对照标准答案 |
| 闭环完整性 | F1→F7 全通；F8 可跨会话读到 F7 的数据 | 端到端走一遍并刷新页面 |
| 可用性 | 无 Key、无网、无安装可完整演示 | 断网演示 |

### 7. 第一部分的需求汇总（一句话各条）

1. 四个用户、两套诉求 → **产品必须分两层**（即时答疑 / 长期沉淀）
2. 概率论答案可验证 → **"验证"是唯一硬差异化**，其余都是包装
3. 错误模式有限 → **错因诊断不需要学生数据**，现在就能做
4. 知识点有依赖 → **错题必须按知识点记**，否则无法回溯根源
5. 学习 = 时间维度变化 → **没有持久化作答记录就不配叫"伴学"**
6. 越会解题越像代写 → **提示阶梯是伦理约束的落地点**，必须在数据模型里
7. 没有基线就没有改进 → **评估集是需求，不是"以后再说"**

### 3.2 仓库独立想到了、第一部分也推到了的（**说明推导可信**）

| 第一部分推导 | 仓库对应 | 评价 |

| §1 两套诉求必须分层 | `docs/20` 把悬浮窗收窄为"只读探针"，功能重心移主站 | ★ **独立收敛到同一结论**，说明这个分层是需求内在的，不是拍脑袋 |
| §2 推论 1：验证是硬差异化 | `docs/09` §二 正确性保障链 + A/B/C/D 分级 | ★ 推导一致。仓库还把"分级"本身当成交付物，比我的推导更细 |
| §2 推论 2：错因诊断不需学生数据 | `docs/09` C4「易错点规则库 · 来自教材/教师经验」 | ★ 一致 |
| §5 提示阶梯是伦理落地点 | `docs/21` 计划里的"二步提示"（X5） | ★ 一致（但见 §3.4 的偏差） |
| §6 没有基线就没有改进 | `docs/09` M4「没有它，前面所有改进都无法证明」 | ★ 与我的措辞几乎相同 |
| §4.2 N5 只读 | `docs/20` §1.1 明确"只读，绝不写、不点、不改" | ★ 一致（但实现没跟上，见 §3.4） |

**这一节的意义**：说明仓库的**方向判断是可靠的**。它的问题不在"想错了"，而在"想到了没做到"——这是完全不同性质、也更容易解决的问题。

### 3.3 ★ 第一部分推到了、但仓库没有的（**增量需求**）

这是本文档最有价值的部分，共 6 条。

#### 缺口 1：作答记录（F7）被错误地和"学生建模"绑在一起

**现象**：仓库已有一份**设计得非常好**的作答契约 `contracts/attempt.schema.json`——含 `kc_ids`（知识点）、`hint_used`（用了几次提示）、`duration_ms`（用时）、`attempt_no`（第几次）、`grader`（谁批的）、`expected`（当时的标准答案）。**这正是 F7/F8 需要的全部字段。**

**但它的抬头写着**：

> `description`: "⏸ **预留契约 —— B线挂起，暂不实现。** …整个 B线（学习者建模 / 教师端）的全部模型都吃这一张表"

**问题**：`docs/09` §一 把 B线挂起的理由是 **"依赖真实学生数据（需知情同意 + 学校配合）"**。但 `attempt` 记录**如果是本地、按 `session_id` 匿名、不出校的**，**根本不触发那个前提**——它和现有的 `qa_log` 表在合规上是同一性质（而 `qa_log` 已经跑了 115 行）。

**结论**：把 `attempt` 契约整体挂在 B线 是**过度保守导致的自伤**。错题本（X6）要的正是它，却被一个为别的目的设的门挡住了。

**建议**（这是本文档的第一优先建议）：
1. 把 `attempt` **拆成两层**：**① 作答记录**（本地/匿名/立即做）与 **② 学习者建模**（需 consent/脱敏/伦理审查/继续挂起）；
2. `contracts/attempt.schema.json` 的字段**几乎不用改**——只需在 `student_id` 描述里明确"主站阶段填 `session_id` 即可，`student_id` 留空"，并删掉抬头的"暂不实现"；
3. `docs/17` 给 `X6` 补一句依赖：错题本吃 `attempt`，不吃 B线。

> 这一条把 X6 从"依赖挂起的 B线"变成"现在就能做"，而且**零新增字段设计成本**——契约已经冻结好了。

#### 缺口 2：提示阶梯（F6）需要落进数据模型，而不只是交互

**现象**：`docs/17` 的 X5 要求写清"二步提示的触发条件与阶梯"，但只把提示当**交互**问题。

**第一部分 §5 的推论**：提示阶梯是伦理约束的落地点，**它必须产生数据**——"用了几次提示"要影响掌握度判定，否则约束不可度量、也可被绕过。

**仓库现状**：`attempt.schema.json` 的 `hint_used` 字段**已经想到了这一点**（注释写着"★ 两个最容易漏掉、但缺了模型就废的字段之一"）。**契约比任务书想得更远**。

**建议**：X0（`docs/21`）设计提示阶梯时，**显式规定每次提示都要能映射到 `hint_used` 的计数**，并在错题本里如实展示"这道题你用了 2 次提示才对"。否则会出现"提示随便点、掌握度照样算满分"的假数据。

#### 缺口 3：没有任何需求规定了"老师"这个角色（S3）

**现象**：仓库的四个用户视角里，`docs/08` B线（教师端）被整体挂起，**主线上没有任何一处为 S3 服务**。`docs/09` §一 的理由（教师端依赖学生数据）在**教师端做建模分析**时成立，但——

**第一部分的推论**：S3 的核心诉求不是"看到分析报表"，而是**"确认学生没在抄"**。而"是否在用提示阶梯"恰恰是**不需要任何学生数据就能对老师暴露**的信号。

**建议**：这一条**不是要求本轮做教师端**，而是一个**低成本的前瞻性建议**：
- 主站如果有一个"本次会话用了 N 次提示才完成 M 题"的自陈视图，对老师就**已经**说明了很多；
- 若以后要启动 B线，`attempt` 的 `hint_used` / `attempt_no` / `duration_ms` 已经为它准备好了——**前提是现在开始记**。
- **反过来说：如果现在不记，将来 B线启动时，历史数据是空白的。** 这是"现在多花 10% 力气、将来省一轮返工"的典型。

#### 缺口 4：没有需求规定"错误答案必须被拦住"的**度量方式**

**现象**：`docs/09` 有很完整的"正确性保障链"（形式化 → 多路求解 → 交叉比对 → 逐步骤校验 → 约束检查 → 反向代入），但**验收标准是"数值题 100% 走重算"这类过程指标**，不是**结果指标**。

**第一部分 §6** 定的是结果指标：**"注入已知错解，统计拦截率"**。

**区别很重要**：
- 过程指标（"100% 走重算"）可以被满足而毫无效果——**恰好仓库现在就是这样**：级别恒为 D，代码"走了流程"但一步真验证都没做（实测：`verifier` 无 SymPy 调用，唯一"独立"动作是又查一次 `kb_search`）。
- 结果指标（拦截率）**无法自欺**：往流水线灌 20 个错答案，必须有 ≥X 个被标注或拦住。

**建议**：给 `docs/09` M1 与 `docs/17` C2 补一条**可机验的验收**：
```
构造 N=20 道已知错解（每道一个确定性错误：方向颠倒/漏完备组/单位错/n 乘错）
→ 跑流水线 → 断言：被标注为"存疑/不一致"或级别降级者的比例 ≥ X%
```
这比"实现多路求解"这种交付物描述更能证明需求被满足。

#### 缺口 5：进度视图（F11）的数据源错了类型

**现象**：`/api/stats/{session_id}` 读的是 `qa_log`——**问答记录**。`analytics` 页展示"累计问答 0 / 最近记录"。

**第一部分 §3** 指出：S2（备考学生）要的"我哪里有薄弱"，**只能从作答记录推**。问答记录回答的是"他问过什么"，不是"他会不会"。一个人可以问 100 次而一次都没答对。

**建议**：`analytics` / 错题本页的数据源应为 `attempt`，`qa_log` 降为辅助（"他关心什么话题"）。两者都留，但**不要让"问答数"冒充"学习进度"**——这是 `docs/17` §六 已列的第 8 条已知限制（`mastery` 0 行）的**需求层根因**。

#### 缺口 6：N8 可访问性从未进入任何需求文档

**现象**：我实测 `docs/*` 与 `contracts/` 中**没有任何一处**提到对比度、键盘导航、点击目标尺寸、`aria`。而实测结果是：正文对比度 2.56:1（需 4.5）、7 个点击目标 < 32px、`aria-*` 全仓库 5 处、**浏览器返回键失效**。

**为什么这算需求缺口而不是实现缺陷**：因为**没有任何验收项**要求它。没人违反规定——是规定里没有这一条。

**其中"返回键失效"已经不只是可访问性问题**：它是**功能缺陷**（实测：点导航正常，按浏览器返回只有 URL 变、视图不变）。而主站的刷题页/错题本**必然需要可寻址 URL**，否则"刷到第 3 步提示"不能刷新、不能分享、不能回退。**这一条建议在 X4 动工前修掉**，否则四个页面各自发明一套状态管理。

### 3.4 ★ 仓库做了、但第一部分认为有偏差的（**需要重新论证**）

反过来也要查：仓库的决策有没有和需求冲突的地方。

#### 偏差 1：悬浮窗的"只读"红线与自己写的最强卖点冲突（**最需要裁定的一条**）

**仓库的两种说法**：
- `docs/20` §1.1：悬浮窗**只读**，"绝不写、不点、不改"，"**驱动动画**"被列入**作废清单**。
- `docs/12` §二 / README：把"**一边讲解，一边把动画走到对应的那一步**"列为**卖点**。

**实测现状**：驱动代码**仍在**（`anim-bridge.js:256` `btn.click()`、`assistant.js:870` 调 `control('step')`）。`docs/17` 的 `X3` 已决定**暂缓**改造，并诚实提示"改造前不要对外说悬浮窗是只读的"。

**第一部分的判断**：这两者**不是简单的对错，而是两种产品定位**，且**我倾向支持 `docs/20`（只读）**，理由比仓库给得更强：

| 论据 | 说明 |
|---|---|
| **合规**（仓库已给） | 修改宿主页面 = 篡改平台内容。这条成立但不够强——因为"点一个播放按钮"在观感上很难被视为篡改 |
| **★ 可靠性**（仓库未给） | 驱动动画**依赖宿主 DOM 的私有选择器**（`#playBtn`/`#startBtn`/`#stepBtn`）。这意味着：**平台一改版，助手就坏**，而且是静默坏（点不到就不点）。只读的失效面小得多——读不到就是读不到，可检测 |
| **★ 卖点一致性**（仓库未给） | 项目最硬的卖点是"**知道自己什么时候不确定**"（`docs/09` §七）。一个敢代你点按钮的助手，**人格上**与"不敢乱说"是矛盾的 |

**但必须以需求为准的反驳**：如果 S1 学生的真实痛点是"动画演到第 5 步我没看懂，想让助手把它停在那一帧讲"，那么只读**确实损失了价值**。

**建议**：这不是技术问题，是**需要用户验证的假设**。如果本轮没条件做用户测试，那么——
- **保留只读作为默认**（`docs/20`），因为它的**失效面更小、合规更稳、人格更一致**；
- 但**不要在文档里把"动画驱动"写成已删**（现在 `docs/20` §二 的表格写的是"新形态取消这个方向"，而代码还在）——这是**文档与代码的既存漂移**，`G2` 应登记；
- 把"驱动动画"**明确标记为"待用户验证"**，而不是"已作废"。**作废需要证据，暂缓只需要理由。**

#### 偏差 2：X0 被写成"文档任务"，但它其实是**需求确认任务**

**现象**：`docs/17` 的 X0 交付物是"一份可据以施工的设计规格"（页面线框 + 交互流程 + 数据模型），验收是"文档里有这些章节"。

**第一部分的判断**：X0 列的**三样东西里有两样其实是需求工作**——
- "**二步提示的**触发条件与阶梯"：这是**需求**（学生什么时候该得到多少帮助），不是设计。
- "**数据模型**：题目集/作答记录/错题/知识点/掌握度"：这是**需求**（记什么才能支撑什么功能），也不是设计。

**风险**：如果 X0 按"文档任务"做，容易产出"页面长什么样"的线框，而**跳过"为什么是这些字段"**——于是数据模型会由 UI 反推（"这个页面要显示什么就加什么字段"），而不是由需求推导。**§3.3 的 6 条缺口正是这么漏掉的。**

**建议**：X0 的验收里补一条**可断言的**：
> 数据模型的每个字段，必须能给出一条**它支撑哪个需求 ID**（F7/F8/F9/F11）的说明；**说不出用途的字段删掉，说不出字段的需求补上**。

这一条能把 X0 从"画线框"变成"验需求"，而且**成本几乎为零**。

#### 偏差 3：把"多智能体协作"当卖点，但需求侧它服务的是评委（S4）而非学生（S1/S2）

**现象**：README 首屏、`docs/01`、`architecture` 页、协作轨迹可视化——**多 Agent 是仓库的叙事中心**。

**第一部分的判断**：从需求看，**S1/S2 不关心有几个 Agent**。学生只关心"对不对、快不快、我错在哪"。多 Agent 服务的是 **S4（评委）**和 **N1（可验证性）的实现手段**。

**这不是说它错**，大创项目服务 S4 是**合理且必要**的。但**建议明确写出来**，否则会有两个真实代价：

1. **工程代价**：为了"协作可见"投入的界面（`runs` 轨迹页、`architecture` 页、`assistant` 页共 ~1400 行）**已经是前端最大的代码块**，而功能页反而很薄（solver 192 行、knowledge 157 行）。**代码重心在演示叙事，不在产品表面。**
2. **需求代价**：真实用户（S1）第一次打开时，看到的是一堆关于 Agent 的解释。

**建议**：
- 主站导航把 `architecture` / `assistant`（演示叙事）**降为二级或移入"关于"**，首页给 S1/S2 的东西让位；
- 在 `docs/15`（口径对照）里**明确区分**："多 Agent 是本项目的**技术路线与评审亮点**，不是学生价值主张"——学生价值主张只有一句话：**"给你答案，并告诉你这个答案经过了几层验证"**（`docs/09` §七 已写好，只是被多 Agent 叙事盖住了）。

## 第三部分 · 给下一步（前端构造）的结论

把两部分的对照压成可执行的结论。

### 4.1 六个缺口 → 对应动作

| 缺口 | 动作 | 归属任务 | 成本 |
|---|---|---|---|
| ① 作答记录被绑进 B线 | 拆分 `attempt` 契约：**记录层立即启用**（`session_id` 匿名），建模层继续挂起；删掉抬头"暂不实现" | **X6**（并修 `contracts/`） | **小**（字段已冻结） |
| ② 提示阶梯要产生数据 | `docs/21` 规定每次提示映射到 `hint_used`；错题本如实展示 | **X0** | 小 |
| ③ 老师角色（S3）无需求 | 主站提供"本会话用了 N 次提示"的自陈视图（**不需要学生数据**） | **X4/X6** | 小 |
| ④ 无拦截率度量 | 补"注入 20 道已知错解，统计拦截/降级比例"为可机验验收 | `docs/09` M1 / **C2** | 中 |
| ⑤ 进度数据源错类型 | 进度/薄弱以 `attempt` 为准，`qa_log` 降为辅助 | **X6/X1** | 小 |
| ⑥ 可访问性无需求 | 补 N8 需求；**其中路由 `hashchange` 必须在 X4 前修** | **X4 前置** | 小 |

### 4.2 必须在 X4 动工前修掉的两件事

这两条会以**乘法代价**影响四个新页面：

1. **前端路由没有 `hashchange` / `popstate`**（`frontend/app/core/router.js:115` 只写 `location.hash`；全仓库 grep 无监听）。实测浏览器返回键只有 URL 变、视图不变。→ 主站的可寻址 URL、提示步进度、错题重做**全部依赖它**。**~60 行。**
2. **`grade_answer` 没有任何 REST 出口**（确定性引擎已就绪、16 项测试通过，但 21 个路由里没有批改端点）。→ 刷题页（X5）的核心链路断在这里。**且建议明确：批改走 REST，不走 LLM**——F4 要求的"即时"与 N1 要求的"可验证"，都不该交给概率模型。

### 4.3 一句话结论

> **仓库的需求方向是对的（§3.2 有 6 处独立收敛可证），工程底子也是扎实的（100 测试 / 46 契约项 / 25 自检全绿，且文档诚实度罕见）。**
>
> **真正的缺口不在"想到没做到"，而在"记录层被错误地挂起"**——`attempt` 契约已经冻结好了、字段设计甚至比任务书更周到，却因为一个为"学生建模"设的合规门槛而无法启用。**错题本（X6）要的正是它。**
>
> 所以下一步最划算的动作不是先写前端，而是**先花半天把 `attempt` 拆层、把 `hashchange` 补上、把批改的 REST 出口定下来**。这三件事都很小，但决定了四个新页面能否并行开发。
