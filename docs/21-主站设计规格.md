## 一、主站是什么、不是什么

### 1.1 定位（引自 `docs/20` §1.2，不重述理由）

主站是**功能重心**：悬浮窗只负责「读屏 + 提问 + 一个进入主站的入口」，
一切需要**停留、操作、积累**的功能都在主站。

### 1.2 本轮范围（7 个页面）

| # | 页面 | 本轮做什么 | 不做什么 |
|---|---|---|---|
| 1 | **首页入口壳** | 导航 + 各功能入口 + 学习概览 | 不做运营位/公告 |
| 2 | **题库** | 列表 + 筛选（章节/难度/知识点） | 不做搜索框（题库 <100 道时无意义） |
| 3 | **刷题** | 出题 → 作答 → 判定 → 二步提示 → 解析 | 不做计时考试模式 |
| 4 | **错题本** | 错题归类（按知识点）+ 重做 | 不做错题导出 PDF |
| 5 | **知识图谱** | 知识点网络 + 依赖边 + 进度着色 | 不做编辑（图谱由内容负责人维护文件） |
| 6 | **动画库** | 既有 8 动画的浏览 + 详情 | 不做上传 |
| 7 | **分布可视化** | 既有 SymPy 推导页归位 | 不改算法 |

> **`docs/20` §1.2 明确本轮不做**：掌握度热力图、PDF 阅读器 / 教材溯源定位。

### 1.3 与既有 9 个展示页的关系

`docs/17` `D1` 已裁定**不剪枝**。处置如下：

| 既有页面 | 处置 |
|---|---|
| `workbench` | **改造为首页入口壳**（`X4`） |
| `knowledge` / `solver` / `visualize` | 保留，归入「学习」组；`solver` 与 `X5` 刷题**共用组件**（见 §7.2） |
| `animations` / `visualize` | 归位为「资源」组（`X8`） |
| `analytics` | **改造为错题本入口 + 学习数据**（`X6`） |
| `runs` | 保留（协作轨迹，服务评委） |
| `architecture` / `assistant` | **降为二级**（见 `docs/22` §3.4 偏差 3） |

> **导航分组建议**（改 `feature.json` 的 `group`/`order`，不手改 `features.registry.js`）：
> `学习`（知识讲解 · 刷题 · 题库 · 分布可视化）→ `积累`（错题本 · 知识图谱 · 学习数据）
> → `资源`（交互动画 · 运行轨迹）→ `关于`（架构与分工 · 页面助手）

## 二、页面清单与区块线框（验收依据）

> 每个区块给一个**稳定的 `data-block` 名**。`X4`–`X7` 的挂载测试**逐块断言存在**，
> 这就是把「手工看一眼」变成「可断言」的机制。

### 2.1 首页入口壳（`X4`）

```
┌──────────────────────────────────────────────────────────────┐
│ [data-block="home-hero"]                                     │
│   概率论伴学 · 主站        <状态胶囊：Mock / 真模型>            │
│   一句话：做题、改错、看清自己哪里不会                          │
├──────────────────────────────────────────────────────────────┤
│ [data-block="home-continue"]        ← 有未完成会话才出现        │
│   ▸ 继续上次：贝叶斯公式 · 第 2 步提示   [继续]                 │
├──────────────────────────────────────────────────────────────┤
│ [data-block="home-entries"]         ← 6 个功能入口卡            │
│   ┌────────┐ ┌────────┐ ┌────────┐                          │
│   │ 题库    │ │ 刷题    │ │ 错题本  │                          │
│   │ N 道    │ │ 继续    │ │ M 道待重做│                        │
│   └────────┘ └────────┘ └────────┘                          │
│   ┌────────┐ ┌────────┐ ┌────────┐                          │
│   │ 知识图谱│ │ 动画库  │ │ 分布可视化│                        │
│   └────────┘ └────────┘ └────────┘                          │
├──────────────────────────────────────────────────────────────┤
│ [data-block="home-progress"]        ← 来自 attempt 记录         │
│   累计作答 X 题 · 正确率 Y% · 近 7 天 Z 题                     │
│   ⚠️ 数据源必须是 attempt，不是 qa_log（见 docs/22 §3.3 缺口 5）│
└──────────────────────────────────────────────────────────────┘
```

**每条入口卡必须能回答"我为什么点它"**：带一个真实的数字（题目数 / 待重做数），
而不是只有标题。数字取不到时显示 `—`，**不许编造或显示 0 冒充真实值**。

| 可断言验收（供 `X4` 直接抄） |
|---|
| `home-hero` / `home-entries` / `home-progress` 三块存在 |
| `home-entries` 内恰好 6 个入口，且每个含可点击元素与一个数字位 |
| 无 `attempt` 数据时 `home-progress` 显示「还没有作答记录」而非 `0 / 0%` |
| 后端不可达时首页仍渲染，且 `home-progress` 显示明确的降级文案 |

### 2.2 题库（`X5` 前半）

```
┌──────────────────────────────────────────────────────────────┐
│ [data-block="bank-filters"]                                  │
│   章节 [全部▾]  难度 [全部▾]  知识点 [全部▾]      共 N 道        │
├──────────────────────────────────────────────────────────────┤
│ [data-block="bank-list"]                                     │
│   ┌────────────────────────────────────────────────────┐     │
│   │ 全概率公式 · 基本型            ch01 · 基础 · 可批改  │     │
│   │ 某工厂有三条生产线…（题干，最多 2 行）               │     │
│   │ 知识点：全概率公式 / 完备事件组       [开始做题]      │     │
│   └────────────────────────────────────────────────────┘     │
│   …                                                          │
└──────────────────────────────────────────────────────────────┘
```

**★ 安全红线**：列表接口**绝不能返回** `final` / `steps` / `distractors` / `pitfalls`。
这四样是答案与错因，必须在**提交后**才可获取（见 §6.2 的接口设计）。

| 可断言验收 |
|---|
| 三个筛选器可独立与组合过滤，且过滤后计数与后端 `count` 一致 |
| **列表响应体断言不含 `final` / `steps` / `distractors` / `pitfalls` 四个键**（泄题防线） |
| 空结果显示空态文案，不是空白页 |

### 2.3 刷题（`X5` 核心）★

这是本轮**最关键的页面**，也是需求（`docs/22` F4/F5/F6）最密集的地方。

```
┌──────────────────────────────────────────────────────────────┐
│ [data-block="practice-stem"]                                 │
│   ch01 · 基础 · 全概率公式     第 2/10 题        [退出]         │
│   某工厂有三条生产线，甲、乙、丙的产量分别占…                   │
│   P(D) = ?                                                   │
├──────────────────────────────────────────────────────────────┤
│ [data-block="practice-hints"]      ← 提示区（阶梯，见 §4.2）    │
│   已用提示：1 次                                              │
│   💡 第 1 步提示：先找「被划分的那个事件」——三条线构成完备事件组 │
│   [再给一步提示]  [我要看解析（需先提交）]                       │
├──────────────────────────────────────────────────────────────┤
│ [data-block="practice-answer"]                               │
│   你的答案：[ 0.026            ]   [提交判定]                  │
│   支持：0.026 / 2.6% / 13/500 / 约等于 2.6%                    │
├──────────────────────────────────────────────────────────────┤
│ [data-block="practice-verdict"]     ← 提交后出现               │
│   ✅ 正确（SymPy 重算一致）                                    │
│   ─── 或 ───                                                 │
│   ❌ 不对。你把 P(次品|甲线) 与 P(甲线|次品) 搞反了              │
│      （命中干扰项：0.06）                                      │
│   ┌─[data-block="practice-evidence"]──────────────────┐      │
│   │ 判定依据：grader=sympy · 置信 1.0 · 定位到第 2 步   │      │
│   └────────────────────────────────────────────────┘      │
├──────────────────────────────────────────────────────────────┤
│ [data-block="practice-solution"]    ← 提交后才渲染              │
│   逐步解析（steps）：1 找完备事件组 0.20 → 2 全概率公式 → …      │
│   易错点（pitfalls）：把三条线的次品率直接平均…                  │
└──────────────────────────────────────────────────────────────┘
```

| 可断言验收 |
|---|
| **未提交前** DOM 中不存在 `practice-solution` 节点（不是隐藏，是不存在） |
| 提交后 `practice-verdict` 出现，且含判定结论 + 依据（`grader` / 置信 / 定位步） |
| 答错时命中 `distractors` 则显示该干扰项的 `message`；未命中则显示 `pitfalls` |
| **答错时响应体不含 `final`/`steps`**（泄题防线，见 §6.4） |
| 每次点提示使 `hint_used` +1，且在 `practice-hints` 可见（`docs/22` 缺口 2） |
| 提交必然产生一条 `attempt` 记录（含 `hint_used` / `duration_ms`） |
| 提交不可解析的答案**不写 `attempt`**，且提示「换个写法」而非判错（见 §6.4 ①） |

### 2.4 错题本（`X6`）

```
┌──────────────────────────────────────────────────────────────┐
│ [data-block="wrong-summary"]                                 │
│   错题 12 道 · 涉及 5 个知识点 · 其中 3 道用了提示才做对         │
├──────────────────────────────────────────────────────────────┤
│ [data-block="wrong-by-topic"]      ← 按知识点归类（不是按时间）  │
│   条件概率     ████████░░ 3 错 / 5 做         [重做这组]        │
│   贝叶斯公式   ██████░░░░ 2 错 / 3 做         [重做这组]        │
│   全概率公式   ████░░░░░░ 1 错 / 8 做  ← 掌握较好              │
├──────────────────────────────────────────────────────────────┤
│ [data-block="wrong-list"]                                    │
│   ex-bayes-01  贝叶斯公式·疾病检测   错 2 次  上次 3 天前 [重做] │
│   ⚠️ 用了 2 次提示才对 —— 掌握度按「非独立答对」计（如实标注）    │
└──────────────────────────────────────────────────────────────┘
```

| 可断言验收 |
|---|
| 归类维度是**知识点**（`kc_ids`），不是时间倒序 |
| 每条错题显示错次与最近时间；`hint_used > 0` 的如实标注 |
| 「重做这组」进入刷题页并带上筛选参数（**依赖 §3.1 的 URL 参数**） |
| 数据源为 `attempt`；`attempt` 为空时显示空态而非 `qa_log` 冒充 |

### 2.5 知识图谱（`X7`）

```
┌──────────────────────────────────────────────────────────────┐
│ [data-block="graph-canvas"]                                  │
│        (节点 = 知识点，边 = 前置依赖，有向)                    │
│   着色：已掌握 / 薄弱 / 未学（三态，来自 attempt 聚合）         │
│   点击节点 → [data-block="graph-detail"] 显示该点的题与错题      │
├──────────────────────────────────────────────────────────────┤
│ [data-block="graph-weakpath"]                                │
│   你连着错了 3 道贝叶斯题 → 上溯发现前置「条件概率」薄弱         │
│   建议复习路径：条件概率 → 全概率公式 → 贝叶斯公式               │
└──────────────────────────────────────────────────────────────┘
```

**★ 技术提醒（`docs/22` §4.5 / 深审）**：**不要扩 `app/components/chart.js`**。
它是 200 行静态绘图器，无布局、无命中测试、无缩放。二选一：
① 新写 SVG 图谱模块；② 像 vendor KaTeX 那样 vendor 一个小型 DAG 库到 `frontend/vendor/`。

**且**：`X7` 依赖一个**从零建**的 DAG 数据文件（现无此产物）。建议落
`backend/knowledge_base/knowledge_graph.json`，节点 `kc_id` 必须与 `attempt.kc_ids` 同命名空间。

| 可断言验收 |
|---|
| 图谱渲染出 ≥1 个具名节点与 ≥1 条有向边（不是空画布） |
| 节点着色三态与 `attempt` 聚合一致；无数据时为「未学」而非误报「已掌握」 |
| 点击节点有可断言的状态变化（`graph-detail` 出现且含该 `kc_id`） |
| 节点 `kc_id` 与 `attempt.kc_ids` 取值同源（交叉断言，防两套命名） |

## 三、交互流程

### 3.1 路由契约（★ `X4` 前置，必读）

**现状缺陷（实测）**：`frontend/app/core/router.js` 只写 `location.hash`，
全仓库**无 `hashchange` / `popstate` 监听** → **浏览器返回键失效**
（实测：点导航正常，按返回只有 URL 变、视图不变）。

主站**必须**修掉它，否则刷题进度、错题重做、图谱定位全部无法寻址。约定的 URL 形态：

| 路由 | 含义 | 参数 |
|---|---|---|
| `#/` 或 `#/home` | 首页 | — |
| `#/bank` | 题库 | `?chapter=&level=&kc=` |
| `#/practice` | 刷题 | `?q=<item_id>&hint=<0..2>` |
| `#/practice?topic=<kc_id>` | 按知识点成组刷题 | 由错题本「重做这组」进入 |
| `#/wrong` | 错题本 | `?kc=` |
| `#/graph` | 知识图谱 | `?kc=<选中节点>` |
| `#/animations` / `#/visualize` | 资源页 | — |

**规则**：
1. `navigate(route, params)` 必须把 `params` 编进 hash（现在收了 `params` 却丢弃）。
2. `initialRoute()` 必须解析参数，**刷新页面后状态可恢复**。
3. 监听 `hashchange` → 走与 `navigate` 相同的渲染路径（**避免两套代码**）。

> ⚠️ 实现时注意：`navigate` 里 `addEventListener(ev, markUserScroll, {passive:true, once:true})`
> 注册的 `wheel`/`touchmove`/`keydown` 三个全局监听**从不被移除**
> （`once` 只在触发时移除；不滚动就永久留存）。改为 `hashchange` 后导航更频繁，
> 泄漏会更明显 —— 顺手一并清理。

| 可断言验收 |
|---|
| 按浏览器返回键，视图**真的切换**（标题与内容都变），不只是 URL 变 |
| 直接打开 `#/practice?q=ex-bayes-01&hint=1`，页面处于该题且已显示第 1 步提示 |
| 刷新页面后 `#/practice?q=…&hint=1` 状态保持 |
| 连续导航 20 次后，`window` 上的 `scroll` 类监听数量不增长 |

### 3.2 刷题完整步序（含状态机）

```
                   ┌─────────────┐
   进入 practice ──▶│ ① 出题      │  取题干（不含答案）
                   └──────┬──────┘
                          │ 学生可重复点「提示」
                          ▼
                   ┌─────────────┐   hint_used: 0 → 1 → 2   （阶梯见 §4.2）
                   │ ② 提示中    │   step 2 后按钮变为「我要看解析」（仍需先提交）
                   └──────┬──────┘
                          │ 点「提交判定」
                          ▼
                   ┌─────────────┐   调 POST /api/practice/grade（deterministic，不走 LLM）
                   │ ③ 已判定    │   同时写 attempt（server 侧写，非前端）
                   └──────┬──────┘
              ┌───────────┴───────────┐
              ▼                       ▼
      ┌──────────────┐        ┌──────────────┐
      │ ④a 正确       │        │ ④b 错误       │
      │ 显示 steps    │        │ 显示错因诊断   │
      │ + 判定依据     │        │ + pitfalls    │
      └──────┬───────┘        └──────┬───────┘
             └───────────┬───────────┘
                         ▼
              ┌─────────────────────┐
              │ ⑤ 已出解析           │  此时才渲染 practice-solution
              │ [下一题] [加入错题本] │  错误时默认已加入
              └─────────────────────┘
```

**关键设计约束**：
- **③ 之前不得渲染 `steps`**（DOM 里不能有，不是 CSS 隐藏）。
- **判定必须在服务端**：前端不得持有标准答案做本地比对（否则答案随前端下发）。
- **`attempt` 由服务端在判定时写入**，不让前端上报（防篡改、防漏记）。

### 3.3 错题本重做流程

```
错题本 [重做这组(topic=kc_bayes)]
   → 跳 #/practice?topic=kc_bayes
   → 按 topic 取该知识点的错题集合（attempt 聚合，去重取最近）
   → 逐题重做；新 attempt 的 attempt_no = 该题历史最大 + 1
   → 连续答对 2 次后从「待重做」列表移出（口径写死在此，避免各人理解不同）
```

### 3.4 从悬浮窗进入主站

`X3`（只读改造）暂缓，故本轮**先不做悬浮窗入口**，直接 `/` 访问即可验收（`docs/17` `X4` 验收 4 已如此规定）。

## 四、★ 二步提示的阶梯（`X0` 要求写清的部分）

### 4.1 为什么提示阶梯是需求而非装饰

`docs/22` §5 的结论：工具越擅长解题，越接近「作业代写器」。
提示阶梯是**伦理约束的落地点**——它把「抄答案」变成「要点两下」的摩擦。
**且它必须产生数据**（`hint_used`），否则约束不可度量、也可被绕过。

### 4.2 阶梯定义（**唯一权威，写死在这里**）

| 层 | 触发条件 | 给什么 | 数据来源 | **不给**什么 |
|---|---|---|---|---|
| **L0** | 初始 | 只有题干 + 作答框 | `core.json` 的 `problem` | 不给任何方向 |
| **L1** | 第 1 次点提示 | **一句话方向**（哪个概念 / 哪类公式） | `examples.json` 的 `hint` | 不给数值、不给公式 |
| **L2** | 第 2 次点提示 | **步骤骨架**：各步 `title`（"找完备事件组"…） | `core.json` 的 `steps[].title` | **不给 `expr` 数值** |
| **解析** | **必须先提交** | 完整 `steps`（含 `display`）+ `pitfalls` | `core.json` 的 `steps`/`pitfalls` | — |

**计数口径**：`hint_used` = 学生点过提示的次数（0/1/2）。解析不计入。
重做时 `hint_used` **重新从 0 计**（每次尝试独立），历史值随各自 `attempt` 保留。

**降级**：某题缺 `hint` 时，L1 直接给 `steps[0].title`，并在 UI 标注「本题无方向提示」——
**不许静默跳过**（`docs/22` N2 诚实原则）。

### 4.3 提示对掌握度的影响（口径写死）

`docs/22` 缺口 2 指出：不能出现「提示随便点、掌握度照样算满分」。
本轮口径（写入 §5.3 聚合规则）：

| 情形 | 计入掌握度 |
|---|---|
| `hint_used = 0` 且正确 | **独立答对**（满分权重） |
| `hint_used ≥ 1` 且正确 | **提示后答对**（降权，UI 如实标注） |
| 错误 | 计错 |

### 5.3 掌握度聚合（`mastery` 表 —— 既有，0 行）

**既有表结构**（`student_mastery`）：
`user_id · topic · attempts · correct · updated_at`

> ⚠️ **主键口径已修正**：原设计是 `(session_id, topic)`。有了账号之后，同一个人换个浏览器
> 就是另一个 session，按 session 聚合会把一个人的掌握度拆成好几份 —— 所以主键改为
> `(user_id, topic)`。迁移脚本会为老数据建一个不可登录的 `usr_history` 账号承接。

**聚合规则（本规格裁定）**：
- `topic` = 知识点 id（`kc_ids` 的每一项各计一次）
- `attempts` = 该知识点的作答次数
- `correct` = **仅计「独立答对」（`hint_used = 0` 且 `correct = true`）**
  → 提示后答对**不进 `correct`**，但进 `attempts`。
  这样 `correct/attempts` 自然反映「独立掌握率」，无需加字段。
- `weak_topics` 排序（`learning_stats` 既有逻辑：按正确率升序）可直接复用。

> **为什么这样定**：`mastery` 表只有 5 列且已冻结；用「独立答对才计 correct」
> 在不改表结构的前提下表达了 §4.3 的口径。若将来要区分「提示后答对」的比例，
> 再从 `attempt` 现算即可（原始记录都在）。

### 6.2 ★ 批改必须走 REST，不走 LLM Agent（**已裁定：照此执行**）

> **裁定（2026-09-16，架构/契约负责人 R1）：✅ 批准。**
> 理由见下，三条都成立。**同时确认一处口径**：`grader.grade()` 的**算法**不改，
> 但**出口必须裁剪**（§6.4 已实测列出要裁哪些字段）——
> 二者不矛盾，"算法不改"不等于"可以直接把返回值发出去"。
> `contracts/api.md` 会随之更新，属兼容性新增。
> **`docs/21` §9 第 1 项据此关闭。**

**理由**（`docs/22` F4/N1）：
1. **确定性**：答案是数值，`grader.grade()` 用 SymPy 做等价比较（`1/4` = `0.25` = `25%`），
   已是 387 行 / 16 项测试的确定性代码。用概率模型解确定性问题会引入本可避免的误差。
2. **即时性**：`F4` 要求纯计算题端到端 < 1s。走 LLM 一轮实测一次完整协作
   **192 帧 / 31.4 KB**，比本地判定慢几个数量级。
3. **保住卖点**：项目的核心卖点是「生成 / 验证分权」。让 LLM 既出题又批改，
   会把「验证」降级为模型自述。

**实现要点**：`backend/app/api/system.py:100` 的 `_NullCtx` 已示范「无 ctx 直接调工具」，
照此新增 practice 路由即可。**`grader.grade()` 本身无需修改**——但**响应必须经裁剪**，见 §6.4。

**红线**：
- `GET .../questions` 响应**不得含** `final` / `steps` / `distractors` / `pitfalls`；
- 判定由**服务端**做，前端不做本地比对；
- `attempt` 由**服务端**写入，前端不上报（防篡改）。

### 6.4 ★ `grade()` 的真实返回与必须做的裁剪（实测得出，**实现前必读**）

实测 `grade(problem_id, student_answer)` 的返回**与直觉不同**，三处必须处理：

**① `verdict` 是中文文本，没有机器可读的 `correct` 布尔值**

实测取值：

| 输入 | `graded` | `verdict` | 含义 |
|---|---|---|---|
| `"0.026"` / `"2.6%"` | `True` | `"正确"` | 正确 |
| `"1/4"` / `"0.03"` | `False` | `"不正确"` | 错误（含定位到第几步） |
| `""` / `"   "` | `None` | `None` | 未作答 |
| `"abc"` | `None` | `None` | **解析失败** |

→ **必须三态处理**：`graded is None` 要区分「未作答」与「解析失败」，
**不许把解析失败当成答错**（否则学生写了个怪格式就被判错，且污染 `mastery`）。

**`attempt.correct` 的映射口径（写死）**：

| `graded` | `attempt.correct` | UI |
|---|---|---|
| `True` | `true` | 正确 |
| `False` | `false` | 错误 + 错因 |
| `None` | **不写 `attempt`** | 提示「没看懂你的答案，请换个写法」（如 `0.026` / `13/500` / `2.6%`） |

**② `grade()` 无条件返回 `final` 与 `steps` —— 这是泄题向量**

实测：**只要答案能被解析（哪怕答错），响应里就带 `final`（标准答案）与全部 `steps`**
（含 `expect` / `expect_display` 数值）。

后果：学生在作答框里敲一个 `0` 提交，就能拿到标准答案。
**这会让 §4.2 的提示阶梯形同虚设。**

→ **端点必须裁剪**：`/api/practice/grade` 只在
**`correct == true`** 或**学生显式点「我要看解析」**（即 `reveal: true`）时返回
`final` / `steps` / `pitfalls` / `distractors`；否则只返回
`verdict` + `message` + 命中的干扰项 `message` + 定位到的步号。

> ⚠️ 注意：`grade_answer` 这个 **LLM 工具**保持原样（它服务 `solver`，
> 需要完整解答）。**裁剪只加在 REST 层**，不要改 `grader.grade()`。

**③ `steps[].matched` 的语义**

实测：`matched` 表示「该步的期望值出现在学生答案里」——
学生答对时**只有匹配上的步为 `true`**（实测 `0.026` 的第 1 步 `matched=false`），
答错时全为 `false`。因此**不能用 `matched` 判断"他会不会这一步"**，
它只在「答对」分支里用于高亮学生真正走过的步骤。错因定位要用 `message` 里给出的步号。

| 可断言验收（补充） |
|---|
| 答错时响应体**不含 `final` / `steps`**（泄题防线，与 §8 `X5` 同一断言） |
| 显式带 `reveal: true` 后响应才含 `steps` |
| 提交 `""` 与 `"abc"` 均不写 `attempt`，且 UI 给出「换个写法」提示而非判错 |
| 答对时写入 `attempt.correct=true`；答错写入 `false`；解析失败不写入 |

### 7.1 ★ 验证级别的展示（`X1`，与 `X5` 强耦合）

`X1` 是 P0 且**当前前端零处理**（实测 `frontend/` grep `verification` 零命中）。

**⚠️ 必须避开的陷阱**：实测 `verification.report` 的报文里，

| 禁止文案 | 「已校验」等笼统表述 |
| 位置 | **回答区显著位置**，不得藏在折叠面板 |

> ⚠️ 另注：实测**级别恒为 D**（`docs/22` §3.1；`MANIFEST.json` `GAP-4` 已更正）。
> `X1` 把级别显示出来后，学生会看到"永远是 D"。这不影响 `X1` 的正确性
