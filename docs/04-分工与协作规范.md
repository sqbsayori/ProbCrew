# 04 · 分工与协作规范

> 面向：全体 5 人。目标是把《项目方案_多智能体学习部署规划》的 R1–R5 落到**具体文件和目录**上，
> 让"谁负责什么"没有歧义，"怎么改不冲突"有明确规则。

---

## 1. 为什么这个骨架能做到"零冲突"

多人协作的冲突源几乎总是这几类文件：注册表、路由表、导航数组、`__init__.py`、共享配置。
本骨架把它们全部改成**自动发现**：

| 冲突源 | 传统做法 | 本骨架 |
|--------|---------|--------|
| 注册 Agent | 改 `agents/__init__.py` | 扫描目录，声明 `SPEC` 即可 |
| 注册工具 | 改注册表 | 扫描 `@tool` 装饰器 |
| 注册 API | 改 `main.py` | 扫描导出 `router` 的模块 |
| 注册页面 | 改导航数组 | `gen_registry.py` 扫描 `feature.json` |
| 动画清单 | 改前端列表 | 读 `manifest.json`（数据文件，逐条追加） |

剩下的**唯一共享可变文件**是 `backend/app/agents/_router.py` 的 `INTENT_AGENTS` 字典
（把意图映射到 Agent）。它的改动形态是"加一个 key"，几乎不会冲突；
而且 `AgentRegistry.by_intent()` 提供了兜底发现，必要时可以完全不改。

## 4. Git 工作流

```
main         ← 只接受来自 dev 的合并，永远可演示
 └── dev     ← 集成分支，每天至少一次集成
      ├── feat/r1-knowledge-agent
      ├── feat/r2-hitl-retry
      └── fix/r3-gamma-cdf
```

**规则**

1. 分支命名：`feat/<角色>-<简述>`、`fix/<角色>-<简述>`、`docs/<简述>`。
2. **一人一目录**：PR 的 diff 应集中在你自己 Own 的目录里。
   若必须碰共享文件，在 PR 描述里**单独列出并说明原因**。
3. **PR 必须至少 1 人 Review**；涉及 `kernel/` 或 `contracts/` 的必须有对应 Owner 参与。
4. **合并前必过**：`python scripts/smoke_test.py` 全绿 + `python scripts/gen_registry.py --check`。
5. 提交信息用中文或英文皆可，但必须能看出改了哪个模块，例如：
   `feat(knowledge): 支持按章节过滤检索`
6. **不要提交**：`.env`、`backend/data/*.sqlite`、`__pycache__`、大文件教材原始 PDF。

**建议的 `.gitignore` 补充**

```gitignore
.env
__pycache__/
*.pyc
backend/data/*.sqlite
frontend/vendor/katex/fonts/     # 可选：字体体积大，也可保留以保离线
```

## 5. 协作纪律（这几条能省下大量返工）

### 5.1 契约先行

要新增事件字段 / artifact kind，**先在群里说，改 `contracts/` 和 `docs/02`，再写代码**。
典型错误是后端先发了新字段，前端不知道，联调时才发现。

### 5.2 跨 feature 禁止互相 import

前端 `features/A/index.js` **不允许** `import` `features/B/`。
需要通信就走 `core/bus.js`：

```js
// A 页面
bus.emit('mistake:highlight', { topic: '条件概率' });

// B 页面
bus.on('mistake:highlight', (p) => { /* ... */ });
```

**理由**：直接 import 会产生循环依赖与隐式耦合，一个人改动会打崩别人的页面。
（唯一的例外是 `components/` 与 `core/`，它们是被设计为共享的。）

### 5.3 复用 run-panel，不要重写

知识讲解 / 题目讲解 / 分布可视化三页都是 30 行左右，因为它们复用了 `components/run-panel.js`。
新页面请照做 —— 流式渲染、KaTeX、轨迹、产物、HITL、取消、节流都已经处理好了。

### 5.4 样式只写在自己的目录

页面私有样式写 `<feature>/styles.css`；两个页面都要用的，**提升到 `components.css`**
（本项目里 `.wb-hero`、`.dist-chip` 就是这么处理的，可参考 git 历史）。

### 5.5 挂载了动画就必须在 unmount 里销毁

```js
export function unmount() {
  panel?.destroy();    // 里面有动画 iframe，不销毁会一直烧 CPU
}
```

### 5.6 别把模型当计算器

凡是能符号计算/规则判断的，不要交给 LLM。加一个新的数学能力时，
先问："这个能不能用 SymPy 算？" 能就写进 `domain/` + `tools/`，LLM 只负责措辞。

## 7. 冲突升级路径

| 情况 | 谁拍板 |
|------|--------|

| 进度落后、要不要砍功能 | 全组周会决定，R1 记录 |

## 8. `docs/adr/` 架构决策记录

任何**破坏性**或**难以回退**的决定都要留一份 ADR（Architecture Decision Record）。
模板：

```markdown
# ADR-0001 · 前端采用免构建 ESM 而非 Next.js

- 状态：已接受
- 日期：2026-09-06
- 决策人：R1 / R4

## 背景
团队已有 Next.js 复现经验（math-tutor / eduagents），但本项目要"建立在既有 HTML 动画之上"，
且需要离线、免安装演示。

## 决策
前端采用原生 ESM + 动态 import，不引入打包器。

## 后果
+ 零安装、零构建、改完刷新即生效；新人上手成本极低
+ 与自包含动画的部署方式一致（都由 FastAPI 静态托管）
− 无 TypeScript 类型检查；靠契约 schema + smoke_test 兜底
− 依赖数量增长后模块图会变复杂（用 `gen_registry.py` 与目录扫描缓解）

## 何时重新评估
若单页模块数 > 25，或需要 SSR/SEO，则迁移到 Vite/Next.js。
```

已建议保留的 ADR 主题：
- ADR-0001 免构建 ESM（如上）
- ADR-0002 动画文件只读、靠 manifest 接入
- ADR-0003 生成/验证分权与 HITL 的交互顺序
- ADR-0004 Mock Provider 必须长期保留（不是临时脚手架）
