# 17 · 模块化任务书（可直接分配）

> **用途**：分工的输入。本文按**可独立交付、互不冲突的模块**切分任务，不绑人；
> 每个任务给足**写入范围 / 接口冻结 / 验收标准**，任何人领走都能独立开工、独立验收。
>
> **依据**：`docs/04`（角色与目录归属）、`docs/12`（M0–M6 阶段与完成标准）、
> `docs/09` §二（A/B/C/D 验证分级）、`contracts/`（契约即接口）。
>
> **快照**：分支 `main`，2026-09-13。数字均为实测值（非估计）。

---

## 一、切分原则

1. **以交付物为单位，不以人为单位**：一个任务 = 一个能单独合并、单独验收的东西。
2. **写入范围互斥**：每个任务列出它 own 的文件；两个任务不共享可写文件。
   跨任务的公共文件（`specs.py`、`graph.py`、`events.py`、`contracts/`）**由指定任务独占**。
3. **接口先行**：任何任务只要改动"别人要读的字段/事件"，就是接口冻结任务，必须先合。
4. **验收标准必须可机验**：每条都给一条能跑的测试命令，不接受"人工看一眼"。
5. **一个任务一个 PR**：走 `feature/* → dev`（squash）→ `main`（merge commit，绝不 squash `dev`）。

## 二、接口冻结（先做这两件，否则后续并行会返工）

| 冻结项 | 现状（实测） | 冻结成什么 |

## 三、任务清单

### A1 · 验证报告契约收敛（`verification.report`）★ 关键路径

- **要解决的矛盾**
  - `contracts/verification.schema.json` 要求 `level` + 每条 check 必须有 `method`（枚举 7 种）与 `name`/`passed`；
  - 实测 `verifier.py:185-195` 产出的 report **缺 `level`**、checks **缺 `method`**，且多出 `notes`/`needs_human`/`draft`/`intent`/`traceability` 等 5 个 `additionalProperties:false` 禁止的字段；
  - `verification_report()` 构造器（`kernel/events.py:202`）**全仓库零调用**；
  - 实测真实问答事件流：`run.start → agent.start/end → plan → solver → verifier → run.end`，**无 `verification.report`**。
- **口径（不新造，沿用 `docs/09` §二）**

  | 级别 | 题型 | 手段（映射到 schema 的 `method`） |
  |---|---|---|
  | A | 纯数值题 | `sympy_recompute` + `multi_path` |
  | B | 公式/恒等变形 | `symbolic_equivalence` |
  | C | 应用题 | `multi_path` + `constraint` + `back_substitute` |
  | D | 证明/开放题 | `heuristic`（`passed=false`，`unsupported` 如实列出） |

  `confidence` 上限按 schema 规定：A 可达 1.0 / C ≤ 0.85 / D ≤ 0.4。
- **写入范围**：`backend/app/agents/verifier.py`、`backend/tests/test_verifier.py`(新增)、
  `backend/app/kernel/graph.py`（**仅"发事件"这一处，与 A3 串行**）
- **接口冻结**：`contracts/verification.schema.json` **不许改**（它就是冻结件）；
  若确需扩展，走 ADR + `contracts/CHANGELOG.md`
- **验收（可机验）**
  1. 新增 `backend/tests/test_verifier.py`：用 `jsonschema` **按 schema 校验真实 report 实例**（不是校验 schema 内嵌 examples）
  2. 实测一次 `/api/chat/stream`，事件序列**必须包含 `verification.report`**，且其 `data` 通过 schema 校验
  3. D 级题（证明题）必须出现且 `passed=false`、`unsupported` 非空
- **依赖**：无（可立即开工）

### A2 · 工具门控真正生效

- **要解决的矛盾**：`specs.py:99-101` 写了门控逻辑，但唯一入口 `RunContext.use()`（`specs.py:200`）传 `allowed=None`；全仓库无人传 `allowed`。
- **契约要求**：`RunContext` 必须知道"当前 Agent 声明的工具集"（来自 `AgentSpec.tools`），越权调用抛错。
- **写入范围**：`backend/app/kernel/specs.py`、`backend/tests/test_kernel.py`（追加用例）
- **验收（可机验）**
  1. 新增用例：把当前 Agent 换成声明工具集不含 `kb_search` 的 Agent，调 `ctx.use("kb_search")` → **必须抛错**（现在不会抛）
  2. 现有 7 个 Agent 的既有调用**全部不回归**（`pytest backend/tests -q` 全绿）
- **依赖**：无

### A3 · 工具结果状态（`tool.result.ok`）

  并断言"失败时前端能拿到非 true 的 ok"

**可同时开工的独立模块（彼此无写入冲突）**：

3. **第三批**：`B1`、`B2`、`C1`（消费 A1 的接口）
