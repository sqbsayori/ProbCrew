## 一、范围调整说明

### 原计划的问题

原先的 B线方案（`08-B线方案_学习者建模与教师端.md`）以**真实学生作答数据**为前提。
但当前阶段团队**无法确定能否拿到这类数据**（需要知情同意 + 学校配合 + 教师意愿，周期长且不受控）。

**把一个依赖外部不可控资源的方案放在主线上，是计划上的错误。** 现调整如下。

### 调整后的定位

| | 定位 |
|---|---|
| **主线（现在做）** | **一个可靠的概率论解题助手**：可注入第三方课程页、能读懂当前页面、支持题目提问、多 Agent 协作**确保解答正确**、内置知识库检索加强、也能独立成站 |
| **可选（数据到位再启动）** | B线全部内容（学习者建模 + 教师端 + 数据飞轮） |
| **可选（待评估）** | 多模态、IRT 标定、长时程规划等 |

**主线的技术命题只有一条：把「正确」做成可验证的，而不是"看起来对"。**

## 二、主线做什么：正确性保障链

现在系统对"正确"的保障只有三条规则检查（步骤数 ≥3、公式定界符平衡、教材溯源率）。
**那是 lint，不是验证。** 真正的正确性需要下面这条链：

```
                        学生题目 / 页面内容
                               │
                    ┌──────────▼──────────┐
                    │ ① 形式化            │  自然语言 → 结构化 MathTask
                    │   已知 / 求解 / 约束 │  （这是整条链的地基）
                    └──────────┬──────────┘
                               │
        ┌──────────────────────┼──────────────────────┐
        ▼                      ▼                      ▼
  ┌───────────┐         ┌───────────┐         ┌───────────┐
  │ 求解 A     │         │ 求解 B     │         │ 求解 C     │   ② 多路独立求解
  │ 直接求解   │         │ 分情形求解 │         │ 特殊化验证 │      （不同策略，非同一次重试）
  └─────┬─────┘         └─────┬─────┘         └─────┬─────┘
        └──────────────────────┼──────────────────────┘
                               ▼
                    ┌─────────────────────┐
                    │ ③ 交叉比对           │  数值 → SymPy 高精度重算
                    │   不一致 → 触发辩论  │  符号 → 等价性检验
                    │   而不是投票         │  ★ 分歧本身是纠错信号
                    └──────────┬──────────┘
                               ▼
                    ┌─────────────────────┐
                    │ ④ 逐步骤校验         │  相邻步是否等价（逐步转符号）
                    └──────────┬──────────┘
                               ▼
                    ┌─────────────────────┐
                    │ ⑤ 约束检查           │  概率∈[0,1]、方差≥0、
                    │                     │  定义域、整数性、n>0
                    └──────────┬──────────┘
                               ▼
                    ┌─────────────────────┐
                    │ ⑥ 反向代入           │  答案代回原题验证
                    └──────────┬──────────┘
                               ▼
              ┌────────────────┴────────────────┐
              ▼                                 ▼
      ┌───────────────┐                 ┌───────────────┐
      │ 全部通过 → 输出│                 │ 存疑 → 标注   │
      │ 附验证报告     │                 │ + HITL 人工   │
      └───────────────┘                 └───────────────┘
```

### ★ 诚实前提：不是所有题都能"确保正确"

必须分级，不能一概而论。这个分级本身就是一个交付物：

| 级别 | 题型 | 验证手段 | 能达到的保证 |
|------|------|---------|-------------|
| **A** | 纯计算的数值题（求 P(A)、E[X]、Var(X)） | SymPy 独立高精度重算 + 多路比对 | **可完全验证**：数值不一致就一定有问题 |
| **B** | 公式推导、恒等式变形 | 符号等价性检验（`simplify(a-b)==0`） | **可强验证**：能证明等价或找出反例 |
| **C** | 应用题（建模 + 求解） | 多路求解一致性 + 约束检查 + 反向代入 | **可交叉验证**：不能保证绝对正确，但能发现大多数错 |
| **D** | 证明题、开放题 | 只能人工 | **不做承诺**，明确标注"本解答未经自动验证" |

**这个分级必须展示给用户**（在回答里标注），而不是笼统说"已校验"。
不夸大是原型阶段最重要的自律 —— 见 `原型声明.md`。

## 三、主线分阶段计划

> 全部**不依赖学生数据**。合计约 若干轮。

### M1 · 正确性保障链★ 核心

| 子任务 | 交付物 | 验收标准 |
|--------|--------|---------|
| M1.1 形式化 | `domain/formalize.py`：NL → `MathTask{known, goal, constraints, domain}` | 50 道题的形式化准确率 ≥ 85% |
| M1.2 数值校验 | `tools/verify_numeric.py`：所有数值答案 SymPy 重算 | 数值题 100% 走重算；不一致必须报错 |
| M1.3 符号校验 | 复用 `math_check`，接入步骤校验 | 相邻步等价性检查覆盖 ≥ 90% 步骤 |
| M1.4 约束检查 | `domain/constraints.py` | 概率>1、方差<0、n 非正整数等必须被拦 |
| M1.5 多路求解 | `agents/` 新增 2 个解题策略节点 + 比对 | 3 路独立求解；不一致率与误报率有报告 |
| M1.6 反向代入 | `tools/back_substitute.py` | A 级题 100% 执行；能发现注入的错误 |
| M1.7 存疑标注 | 事件协议扩展 `verification_level` 字段 | 回答里明确标注 A/B/C/D 级 |

**关键设计**：M1.5 的"多路求解"**不是同一次调用的重试**，而是**策略不同**的独立求解
（直接求解 / 分情形 / 特殊化验证）。同一次调用的 3 个样本会共享同一个错误前提。

### M2 · 检索加强

| 子任务 | 交付物 | 说明 |
|--------|--------|------|
| M2.1 语料结构化 | 教材 → 带 LaTeX 的 Markdown，按知识点切块 | 见第四节的数据需求 |
| M2.2 向量检索 | Qdrant + BGE-M3（本地） | 保持 `kb_search` 接口不变，Agent 不用改 |
| M2.3 混合检索 | 向量 × 0.7 + BM25 × 0.3 | 公式符号靠 BM25 兜底 |
| M2.4 重排 | bge-reranker-v2-m3 | top-20 → top-5 |
| M2.5 结构化公式库 | `knowledge_base/formulas.json` | 定理/公式的结构化条目，支持精确查找 |
| M2.6 多跳检索 | 一个问题串多个知识点 | 例："贝叶斯的期望" 需要先检索两个概念 |

**验收**：自建 30 题检索集，正确章节召回 ≥ 85%；`kb_search` 接口签名不变。

### M3 · 题型与策略

| 子任务 | 交付物 |
|--------|--------|
| M3.1 题型识别 | 题型的分类（全概率/贝叶斯/分布求解/期望方差/极限定理…）+ 每类的解题套路 |
| M3.2 多解对比 | 同一道题给出 2 种解法并**交叉验证结果一致** |
| M3.3 易错点库 | `knowledge_base/misconceptions.json`（不需要学生数据，来自教材/教师经验） |

### M4 · 评估体系★ 没有它，前面所有改进都无法证明

| 子任务 | 交付物 |
|--------|--------|
| M4.1 自建基准 | `eval/probstat-bench.jsonl`：**≥100 道**概率论题 + 标准答案 + 知识点标注 |
| M4.2 自动评测 | `scripts/eval.py`：正确率 / 形式化成功率 / 验证拦截率 |
| M4.3 失败归类 | 自动分类失败模式（形式化错/计算错/检索漏/表述问题） |
| M4.4 回归门禁 | CI 里跑基准，准确率下降则红灯 |

**验收**：能一句话回答"这一版比上一版好了多少"。

### M5 · 体验与页面感知增强

- 会话记忆（长对话上下文）
- 讲解导出（Markdown / 图片）
- 页面公式识别增强（PPT / PDF 里的公式）
- 移动端适配
- 第三方平台实测（智慧树等，P1 遗留项）

## 六、什么时候可以启动 B线

触发条件（满足其一即可重新评估）：

- [ ] 拿到**至少 1 个班**的学生作答数据（≥30 人 × ≥30 题）且有知情同意
- [ ] 或：拿到**教师明确意愿**——愿意在自己的课上试用一学期
- [ ] 或：明确放弃真实数据，改用 **A6 公开教育数据集**做算法研究（此时 B线降级为"算法验证"性质，不能声称有教学效果）

**在此之前，B线保持挂起**，其技术准备（如 A6 上的 BKT 实现验证）可以作为**主线的附属练习**，
但**不占用主线排期**。

## 七、主线做完之后，能说什么

| | 现在 | 主线完成后 |
|---|------|-----------|
| **对学生** | "能问概率论问题" | "给你答案，并告诉你**这个答案经过了几层验证**、哪一层没通过" |
| **对老师** | "学生多了个问答工具" | "它能自己发现算错了，不瞎给答案" |
| **对技术** | "多 Agent 协作架构" | "**可验证的解题链**：3 路独立求解 + 符号校验 + 约束检查 + 反向代入" |
| **对项目** | 演示原型 | **一个在概率论上"不敢乱说"的助手** —— 这个"不敢"是有技术支撑的 |

**最后一句话是关键**：主线的价值不是"更聪明"，而是"**知道自己什么时候不确定**"。
对一个学习工具来说，这比多答对几道题重要得多。
