# 15 · 口径对照与偏差说明（立项书 ↔ 现行计划 ↔ 仓库现状）

> **这份文档解决什么问题**：现在团队手里有**三份口径不同的计划**，
> 而立项申请书里的量化验收指标和仓库现状有明显落差。
> 如果不把差异**显式写下来**，中期检查/结项时会出现"承诺了但没做、也没人记得为什么"的尴尬。
>
> 本文只做三件事：① 说清三份文档各自是什么；② 逐项对照立项书的指标与仓库现状；
> ③ 给每处偏差标注**理由 + 结项口径建议 + 责任人**。
>
> **维护约定**：本表随实际进展更新；改动只增不删（已完成项标 ✅ 并注明日期）。
> 依据：`立项申请书(20260824).docx`、`项目方案_多智能体学习部署规划.md`、`docs/12`、仓库实测。

## 三、每处偏差：理由 + 结项口径 + 责任人

> "结项口径"是**答辩/结项时怎么讲**的建议措辞——不掩饰、也不自贬。
> 责任人一栏是占位（R1–R5），请团队按实际分工填实。

### 偏差 1 · 产品形态从"学习网站"收窄为"悬浮窗助手"

- **事实**：立项书写的是多模块网页应用 + 管理后台；实际做的是能注入第三方课程平台的悬浮窗，
  核心能力是"读懂学生正在看的这一页"。
- **理由**：`docs/12` 的判断是——平台侧零改动、体验最好（划词、跟随、动画联动），
  且能在真实课件上立刻验证价值；自建网站则需要学生主动迁移，冷启动风险大。
- **结项口径**："我们保留了网页形态作为承载（`/course/` 演示页与站点外壳），
  但把主战场放在学生**已经在用的**课程页面上——这是产品定位的主动收窄，不是能力缺失。"
- **责任人**：R1

### 偏差 2 · 批改闭环（Grader + 题库）—— 🔶 **最小版已落地**（团队已决定"补回来"）

- **事实**：立项书 M3 的核心交付是"questions 题库与自动核验 + Grader 逐步批改 + 错题库"，
  且在创新点里反复出现；而 `docs/12`/`docs/14` 的两个 P0 是"划词解释"和"解题 + 校验"，
  **"批改"在转路线时被静默丢掉了**。
- **理由（客观的）**：批改需要"已核验标准答案的题库"作为前置（立项书原文：
  "Grader 依据 published 标准答案逐步批改"），而题库依赖教材习题，教材尚未拿到。
- **团队决定（2026-09）**：走**路线 1 · 补回来**，先做最小可用版 —— 不等教材，
  用现有 10 道自编例题 + 逐题 SymPy 复算，先把"判定—定位—提炼易错点"跑通。

**最小版落地记录**：

| 项 | 内容 |
|---|---|
| 批改器 | `backend/app/tools/grader.py`（工具名 `grade_answer`，自动发现，无需登记） |
| 题库 | `backend/data/question_bank/core.json` —— **10 道**，覆盖现有例题库全部题目 |
| 标准答案可信性 | `scripts/verify_question_bank.py`：逐题**独立复算**（不读题库数字，另写期望值比对）+ 典型错答有效性检查 |
| 判定方式 | SymPy 符号等价 → 数值近似；**容差按有效数字定**，`0.0265` 判对、`0.03` 判错 |
| 诊断 | 三类：**典型错答**（如贝叶斯漏分母"健康人误判"那一块）、**停在中途**（算到 P(+)=0.05094）、首个不一致步 |
| 易错点 | 来自题库人工提炼，**不是模型现编** |
| 回归测试 | `backend/tests/test_grader.py`（16 项） |
| 题库复核脚本 | 已接入本地验收（10/10 通过） |

**仍未做的部分**（写在明处，别当成已完成）：
1. **题目数量**：立项书要求 M1 出"评测集初版 60 条"、M3 有"questions 题库"，
   现在只有 **10 道**（=现有例题库规模）。扩题依赖教材习题或自编，属"等数据"类工作。
2. **落库**：立项书要求批改结果"写入错题库"（`student_` 前缀表）——
   涉及 L2 学生作答数据，按 `docs/13` 需等 B 线激活；
3. **前端与接口**：`grade_answer` 目前是 Agent 工具，还没有
   `/api/problems/submit` 端点与"提交作答 → 批改报告"的界面（下一步）。
4. **多步批改的粒度**：现在按"题库里写明的步骤"比对；学生自由作答的分步判定
   仍要靠 `verifier` 的 LLM 校验，属于 M3 后半段。

- **结项口径**："批改的难点不在模型，在于**标准答案的可信来源**；
  我们用自己的题库（逐题 SymPy 复算、脚本可复核）保证了这一点，
  并把'判定依据'写进了每一步 —— 学生看到的不是一句'错了'，而是'你算到第几步、错在哪'。"
- **责任人**：R2（主）+ R3

### 偏差 3 · 学习记录 / 画像 / 进度 / 薄弱诊断（F4/F5/F6）整块未做

- **事实**：立项书把它们写成六项需求里的三项，且是"完整学习闭环"的后半段。
- **理由**：`docs/10`/`docs/12` 已明确 **B 线（学生数据 + 教师端）挂起**——
  它依赖真实学生数据与知情同意，属于**外部不可控资源**。
- **结项口径**："F4–F6 依赖真实学生数据；我们把'不依赖学生数据'的部分（检索、校验、可视化）
  做扎实，把依赖数据的分期到 B 线，并已完成数据分级与合规设计（`docs/13`）。"
- **责任人**：R4

### 偏差 4 · 技术选型整体替换（Qdrant/PG/Redis/JWT/Matplotlib/Next.js → 进程内 + SQLite + 静态页）

- **事实**：立项书列了一整套基础设施，仓库实际是"零外部依赖"路线。
- **理由**：少依赖 = 部署门槛低、演示零配置、CI 快；`requirements.txt` 里还专门写了注释
  说明"不需要 Docker、不需要 matplotlib"。检索升级后向量已在进程内跑通，
  且按 `docs/13` 保留了 `DB_URL`/`CORPUS_DIR` 等切换口。
- **风险**：**规模上限**。语料从 22 段涨到教材级（数千段）后，进程内向量与 SQLite 都需要替换。
- **结项口径**："我们按'先证明链路成立、再换实现'的顺序做：接口已冻结，
  换 Qdrant/PostgreSQL 只改实现文件，调用方（Agent）零改动。"
- **责任人**：R5

### 偏差 5 · "验证角色与生成角色模型分离"未落实

- **事实**：立项书把它列为创新点（避免"自己检查自己"），
  但 `kernel/graph.py` 里生成与验证**共用同一个 provider 实例**。
- **理由**：属于遗漏而非取舍——当前只有 DeepSeek 一个通道，`mock` 用于离线。
- **建议**：这个改动**成本很低**（provider 工厂加一个 `role` 参数、配置里允许
  `VERIFIER_MODEL` 覆盖即可），且直接对应立项书的创新点，**性价比很高，建议优先补**。
- **结项口径**："生成/验证分权在**角色、输入、判定规则**上已经分离；
  模型层面也支持配置不同模型/版本，避免自证。"
- **责任人**：R5（工程）+ R2（验证规则）

### 偏差 6 · 评测规模差一个量级（120 条 / 80 条 / 60 条 vs 现有 40 条）

- **事实**：立项书的 F1/F2/M2/M3 都写了明确的评测条数；仓库只有 40 道**检索**标尺题，
  且没有讲解评测、解题评测。
- **理由**：评测集依赖语料（F1）与题库（F2/F3），后两者都缺。
- **建议**：**这是唯一"不需要教材也能立刻推进"的缺口**——
  检索标尺可以继续扩充到 120 条（现有 `scripts/retrieval_questions.tsv`
  就是为这件事准备的骨架），且扩充后 `docs/16` 的数字会自动变成符合立项书口径的证据。
- **责任人**：R4

### 偏差 7 · 三份计划文档并存

- **事实**：立项书、26 周方案、`docs/12` 三套口径；`docs/09` 曾宣布"替代 `docs/05`"，
  现在 `docs/12` 又取代了 `docs/09` 的执行地位。
- **建议**：以本文档为**唯一的口径对照入口**，`docs/05`/`docs/09` 保留为历史；
  新人只要读 `docs/14`（交接单）→ `docs/12`（计划）→ 本文档（偏差）三份即可。
- **责任人**：R1
